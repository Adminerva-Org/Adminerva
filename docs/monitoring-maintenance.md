# Optional monitoring maintenance — prepared, not deployed

This continues PR #22. The current prepared website manifest is `2026.10.19.3`; `.19.1` and `.19.2` were staging versions, not live releases, so public history/notifications omit them and consolidate their changes into `.19.3`. The live `.18.4` history remains unchanged. No production rules, Functions, configuration or student records were changed while preparing this work.

## What is implemented

- `monitoringMaintenance`: an hourly scheduled handler. A missing or disabled `monitoring_control/runtime` record performs no cleanup or summary writes. Both policy flags default off; configuration is not inferred from browser/localStorage roles.
- Cleanup touches only `activity_events` and `issue_diagnostics` with elapsed expiry, at most three 200-record transactions per collection per run. Existing report documents, grades, evidence and revisions are never deleted or updated. A cap is recorded as possible backlog, not falsely reported as complete deletion.
- Optional summaries use the newest 500 events within seven days and the currently assigned instructor sections. Auth identities are resolved in batches of at most 100, then preferences, roster sections and minimal student fields are re-read transactionally before saving. Disabled/unverified accounts, missing profiles, re-assigned identities, withdrawn consent and other sections are excluded. These remain client-reported engagement observations, not verified learning, authorship or effort.
- Student display is capped at 100 with explicit truncation metadata. Only coarse module totals, visits and returning days enter teacher views. No raw owner UIDs, report trails, source code, credentials or student profile tokens enter the projection. Repeated page-open events for one session/module count once, including repeated preference saves.
- A five-minute transaction lease prevents overlap. Each mutation checks the active lease and policy revision. A policy change stops subsequent batches/writes; already-started work may finish. Failed/expired leases can recover on a future run. Status contains operational counts, not student identifiers or exception payloads.
- `activityConsentChanged`: removes revoked/reassigned student rows from the latest snapshot, independently of hourly policy flags. It re-reads current consent, so a delayed old opt-out does not erase a subsequently re-enabled student's current summary. Deleting a preference also removes its previous student row. This handler must be deployed to receive events; delivery/processing can be delayed.
- Manual administrator summary saves now re-read consent, assigned sections and current student sections inside the save transaction, after confirmation. An opt-out processed while the confirmation is open cannot be resurrected by the captured pre-confirmation sample. Manual snapshots still rely on trusted administrator judgement, unlike the worker's extra Auth ownership resolution.
- Teacher views subscribe to snapshot changes, clear rows on permission loss, and identify system refresh versus manual administrator preparation. Changed roster sections and 30-day-old snapshots are denied by rules until refreshed.
- `monitoring_control/runtime` policy changes require verified administrators, a bounded reason, sequential revision and a matching immutable audit. `monitoring_status/runtime` is server-write-only, even for administrator browser clients. Both root collections are excluded from legacy staff catchalls.

## Administrator workflow after an approved rollout

1. Open **Staff Home → Administration analytics** and configure the instructor's sections.
2. Review school privacy/retention policy, expected volume, billing and runtime prerequisites with the owner. Keep both automatic policy switches off until the backend is approved and available.
3. Select the desired cleanup and/or summary-refresh policy, enter a reason, then **Save maintenance policy**. Saving is a configuration write, not a deployment or proof of worker availability.
4. Refresh monitoring after the next run and inspect **Last server result**, counts and cap/backlog warnings. Enabling does not request an immediate run. Disabled policy still leaves any previously deployed Scheduler job in place.
5. If cleanup reaches its cap repeatedly, scale the reviewed retention mechanism, run the bounded manual cleanup repeatedly or approve Firestore TTL. Do not promise deletion exactly at day 30. Account erasure and deletion of separate preferences/snapshots remain an administrator process.

## Release gates — explicit approval still required

I've set up prototype Security Rules to keep the data in Firestore safe. They are designed to be secure for verified administrator controls, immutable policy audits and role-separated monitoring. However, you should review and verify them before broadly sharing your app. If you'd like, I can help you harden these rules.

Before deployment, confirm the existing database ID/edition and compatibility with the repository's Core SDK/rules, functions region and service-account permissions using a fresh authorized session. Emulator validation is not production-edition verification.
- Obtain explicit approval for matching Firestore rules and the two new handlers. Select only the intended handlers; do not inadvertently deploy the unrelated legacy notification functions or publish grades. Deploying a schedule creates server infrastructure that can incur charges even with policy flags off. Review billing and Cloud Scheduler API/IAM first. [Firebase scheduled-function prerequisites](https://firebase.google.com/docs/functions/schedule-functions).
- Coordinate rules, backend and website activation; keep collection consent optional and record a school-approved cleanup procedure before enabling monitoring at scale. The worker uses Admin SDK privileges and bypasses client rules, so review the service-account IAM and the literal monitoring-only write paths. [Firestore transaction semantics](https://firebase.google.com/docs/firestore/manage-data/transactions).
- TTL is an optional separate approval, not configured by this patch. Its deletion is not immediate and does not automatically remove application-derived snapshots; do not substitute an expiry timestamp for an actual retention mechanism. [Firestore TTL behavior](https://firebase.google.com/docs/firestore/ttl).
- Additional teachers remain blocked on a reviewed role/class-assignment migration. Legacy broad academic staff permissions are unchanged; this is not a claim of multi-tenant academic isolation. Strong ingestion rate budgets, longitudinal population analytics and account-erasure automation remain future work.

## Validation

Unit tests compare packaged worker/browser schemas and summary behavior and exercise verified identity/section inclusion and visit deduplication. Real local Firestore tests check disabled policy, bounded cleanup, backlog, stale leases, immutable academic records, current consent/identity revalidation and idempotent consent removal. Rules tests cover policy audit bypass attempts, server-status spoofing, roster/expiry revocation and re-assigned student identities. The extended real Auth/Firestore browser workflow saves audited policy, invokes the actual worker core with emulator Auth identities, sees live teacher updates, and opts out while a manual-summary confirmation is open. This tests the handlers' logic, not production Scheduler provisioning, event delivery or billing. No live data or deployment credentials are needed.

The browser schema and packaged Functions schema intentionally have separate small implementations because Functions deployments only package their source directory. A parity test prevents silent schema/scoring drift; neither implementation produces assessment grades.
